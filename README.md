# OLED 点阵取模工具

给 STM32 + SSD1306 工程配套的点阵取模工具，两条产线共用同一套导出格式：

- **汉字**：输入文字 → 实时看点阵 → 导出 `OLED_CFont.h`，
  一个字一个字地手攒字模这件事就不必再做了
- **图片 / 动画**：一张图或一个 GIF → 二值化成 128×64 点阵 → 导出成 C 数组，
  可以几份素材并存，也可以拼成一段动画

另外会读工程里的 Keil / CubeIDE 配置（`.uvprojx` / `.ld`），
算出 Flash 够不够放这些点阵。

有两种用法，产出格式完全一致，按需要选：

- **图形界面版**（Qt）——适合加几个字、想边看边调字形
- **命令行版**（`src\build_cfont.py`）——适合一次加几十个字，或写进脚本

## 它解决什么

取模最容易出的两个问题，这个工具都从源头消掉了：

1. **取模参数选错**。字模有"列行式 / 逐行式 / 顺向 / 逆向"多种排列，
   和驱动的读取方式不匹配就会显示成一片散点。本工具**格式写死在代码里**，
   不需要你选任何参数。
2. **手抄 32 个十六进制数**。漏一个字节肉眼根本看不出来，上机才发现不对。
   本工具自动生成，并且**导出前逐行校验**（每行必须正好 35 字节）。

再加上点阵实时可看、Flash 占用实时可见、已有字库可导入合并。

## 构建图形界面版

需要：Visual Studio 2022（含 C++ 工具）、Qt 6（msvc 版）、CMake、Ninja。

```
双击 scripts\build.cmd
```

脚本会自动探测这些工具装在哪，并把结果打印在开头。探测不到时才需要改
`scripts\build.ps1` 开头的 `$Fallback*` 变量。

产出 `build\oledmatrix.exe`，双击运行。Qt 运行库会自动拷到旁边。

## 用

### 图形界面版

1. 左下输入要显示的汉字（可以多行，会自动去重）
2. 选**字号**：16×16（默认，每字 32 字节）/ 24×24（72 字节）/ 32×32（128 字节）
3. 右边实时显示点阵
4. 字体选**宋体**、阈值约 **110** 是默认值；字太细就把阈值调小，太粗调大
   （有些字体/字号下汉字是按整像素画的，这条路阈值不参与，见文末「还有一层」）
5. 想做反白显示（亮底暗字）就勾上「取反色」，见下文「取反（反白显示）」
6. 点「导出 OLED_CFont.h」
7. 双击 `src\install-cfont.cmd` 搬运进工程
8. Keil 里 Rebuild

写代码的时候用「**复制为 C 字符串**」：把第 1 步那段文字直接变成能粘进 `main.c` 的
调用句（中文全写成 `\xNN`，粘完就能编）。手打中文串会撞上 armcc 的 GBK 解析，
报 `#8: missing closing quote`——见文末「一处硬要求」。

「导入已有字库」会把现成的 `OLED_CFont.h` 读回来**并合并**（不是替换），可以在它基础上加字。

**如果弹出"导出成功（需要手动搬运）"**：说明程序没有权限直接写工程目录。
按提示双击 `src\install-cfont.cmd` 即可，它会自动备份旧文件。

### 命令行版

改 `src\build_cfont.py` 顶部的 `CHARS`：

```python
CHARS = (
    "嵌入式开发网中文测试"
    "你好世界"
    ...
)
```

然后：

```powershell
python oledfonttool\src\build_cfont.py      # 生成字库，并打印每个字的点阵供核对
```

产出 `src\OLED_CFont.h`，再双击 `src\install-cfont.cmd` 搬运。

只想**再加几个字**、不想重建整份字库，用 `add_chars.py`：

```powershell
python src\add_chars.py 温度报警                       # 只更新 src\OLED_CFont.h
python src\add_chars.py --dir <工程>\Hardware 温度报警  # 顺便装进工程（自动备份）
```

它会读现有字库、自动认出当前字号、只补缺的字、按 UTF-8 排序后写回。
不给 `--dir` 时，会自己向上找**工程文件**（`.uvprojx` / `.ewp` / `.cproject`）
来定位工程——不看工程叫什么名字，也不看你把驱动写成 `OLED.c` 还是 `lcd.c`。

## 烧录自检帧（第一次上机先做这个）

字库里的单个字对不对，肉眼几乎判断不出来；但一整屏的边框歪没歪，一眼就能看见。
「导出」里的 **烧录自检帧…** 就是干这个的。

1. 点「烧录自检帧…」，对话框里直接能看到将要烧进去的图，改字号会跟着变
2. 对话框顶部的**屏尺寸**选 `128×64`（0.96"）或 `128×32`（0.91"）—— 默认跟导出组
   那个「屏」下拉一致。选错的表现是屏上只显示上半截，看着像驱动少写了半屏
3. 点「保存到工程」→ 在 `OLED_CFont.h` 旁边生成 `OLED_SelfTest.h`
4. `main.c` 里加上：

```c
#include "OLED.h"
#include "OLED_SelfTest.h"

OLED_Init();
OLED_SelfTest_Show();      /* 整屏写一次，128×64 是 1KB，128×32 是 512B */
while (1);
```

正常应该看到（128×64 整屏）：

```
+------------------------------------------+
|##                                      []|
|##                                      []|
|                                          |
|               取 模 正 确                 |
|                                          |
|XX                                      ##|
|XX                                      ##|
+------------------------------------------+
```

外框完整、四个角图案各不相同、中间有字 —— 说明工具的输出格式和你的驱动是同一套。

生成的 `OLED_SelfTest.h` 里有个【适配区】，和字库、动画一样只依赖两个最底层的函数：

```c
#define OLED_SELFTEST_WRITE_CMD(c)    OLED_WriteCommand(c)
#define OLED_SELFTEST_WRITE_DATA(d)   OLED_WriteData(d)
```

定位命令（`0xB0|页`、列地址高低 4 位）是函数自己发的，**不调用 `OLED_SetCursor`**。
那个函数各例程参数顺序不一致（中景园是 `(页, 列)`，有的写成列在前），绕开它就不用
对着改，也不会因为传参顺序反了把图打歪。

对不上时按现象查：

| 屏上看到 | 实际原因 |
|---|---|
| 右边框缺两列、整幅左移 2 像素 | 屏是 SH1106（132 列），把「屏控制器」选成 SH1106 重新导出 |
| 画面上下颠倒 | 页序反了，`0xC8` 与 `0xC0` 对调 |
| 黑底白点变成白底黑点 | 极性反了（阳码 / 阴码） |
| 字是花条纹、上下错位 | 位序反了（高位在前 / 低位在前） |
| 有边框但中间没字 | 生成时没勾「包含中文」 |

四个角刻意画成实心、空心、交叉、棋盘四种不同图案：任何整屏翻转、镜像、页序颠倒
都会让角标互相串位，不用放大镜也能发现。

这张图是**整屏直接写显存**，不经过字库查表，所以它验证的是「工具输出 ↔ 驱动写显存」
这一段。字库本身对不对，由导出时的逐行自检保证。

还没装字库、只想先验证屏和接线时，把对话框里的「包含中文」取消勾选，导出的就是
纯几何版本。

## 图片 / GIF 动画

顶部切到 **图片 / 动画** 页，点「添加图片 / 动图…」，可以一次选一个，也可以一次选一堆。
右边实时看单色化效果，可以调目标尺寸、缩放方式、阈值、抖动、抽帧、取反。

### 一次选多个文件时怎么处理

「多选时合成一个动画」这个开关决定同一批文件的去向：

- **不勾（默认）**：每个文件各自成为列表里的一条素材，分别预览、分别设置、分别导出。
  工程里要同时放开机图、logo、几个小图标时用这个 —— 各自尺寸不同、阈值也不同，
  来回换一张导一张会把手上的参数全丢掉。
- **勾上**：按文件名顺序把它们拼成一段动画（`frame2.png` 排在 `frame10.png` 前面，
  用的是数字感知的排序，不是字符串排序）。文件里如果有 GIF，它自己的所有帧先展开
  再接下一条。600 帧上限和 400 MB 内存预算按**整批**算，不是每个文件各算一遍。

某个文件读不出来只会在它自己那条下面标出来，不影响同批的其它文件。

### 素材列表

左边列表里每一条就是一份素材，选中哪条，右边的预览和取模设置就作用于哪条：

- 名字取文件名（去掉扩展名），转成合法 C 标识符；重名自动加 `_2`、`_3`。
- 「移除」删掉选中的一条，「清空」全删（文件本身不动）。
- 列表下面有一行**合计**：几份素材、一共多少帧、一共占多少 Flash，占芯片容量的多少。
  只有一份素材时不显示（那一份的数字下面的详情里已经写了），再挂一行一模一样的
  数会让人以为算了两次。超出芯片容量时直接写「装不下」，不会给你一个 187% 这种
  没法用的数字。
  合计是**按每份自己的尺寸**算完再相加的：列表里 128×64 的动画和 16×16 的图标
  可以混着放，各差 32 倍，不能拿一份的每帧字节乘总帧数。
- 「导出这份 .h」只导当前这条，默认文件名就是 `<素材名>.h`。
- 「全部导出…（每份一个 .h）」选一个目录，每条各写一个 `<素材名>.h`，同名文件会先问一句。
- 「全部存进一个 .h…」把所有素材写进**同一个**头文件，但每份仍然各自独立
  （各自一套宏、数组、`Xxx_ShowFrame()`，不合成一段动画），只有「适配区」
  是全文件共用的一份。每份点阵数组的正上方会注明**导入时的文件名**，
  隔几天回来能认出哪个数组是哪张图。默认文件名 `oled_assets.h`。
- 「一键接入工程…」把上面导出的那个 `.h` 直接接进 Keil 工程：驱动头补函数声明、
  `main.c` 补 `#include`、再补一行 `Xxx_ShowFrame(0)`（插在 `OLED_Init()` 之后，
  先刷第 0 帧看接线和图对不对）。写盘前能逐条预览，每个文件留 `.oledbak` 可撤销，
  执行和撤销都跟文字页那个是同一套。细节见文末「一键接入工程」。

**每份头文件的宏和函数都带素材名前缀**：`logo` 导出来就是 `LOGO_WIDTH`、
`Logo_ShowFrame`、`LOGO_COUNT`，include guard 也是 `__LOGO_FRAMES_H`。
所以几份素材的头文件可以同时 include 进一个工程，不会撞宏定义、不会重复定义数组。
只用一份时前缀就是名字本身，不再是固定的 `ANIM_*`。

打包文件同理：里面每份各有一套前缀，include guard 跟着**文件名**走
（`oled_assets.h` → `__OLED_ASSETS_H`），两个素材包同时 include 也不会互相吃掉。

目标尺寸有五种：`128×64`（0.96"）、`128×32`（0.91"）、`64×64`、`32×32`、`16×16`。
选错的表现是下半屏整块黑、或者整幅压扁 —— 屏多大就选多大。

**导出的头文件自带显示函数**，不需要你工程里存在批量写显存的函数（比如
`OLED_WriteDataBlock` 这种很多例程根本没有的东西）。只要改两个宏：

```c
/* logo.h 里的【适配区】 */
#define LOGO_WRITE_CMD(c)    OLED_WriteCommand(c)   /* 改成你工程的写命令函数 */
#define LOGO_WRITE_DATA(d)   OLED_WriteData(d)      /* 改成你工程的写数据函数 */
#define LOGO_DELAY(ms)       HAL_Delay(ms)          /* 改成你工程的延时函数 */
```

然后正常用：

```c
#include "logo.h"

uint8_t i;
while (1) {
    for (i = 0; i < LOGO_COUNT; i++) {
        Logo_ShowFrame(i);
        LOGO_DELAY(LOGO_DELAY_MS);
    }
}
```

几个要留意的地方：

- **定位命令是函数自己发的**（`0xB0|页`、列地址高低 4 位），不调用驱动里的
  `OLED_SetCursor`。各例程这个函数的参数顺序不一致（中景园是 `(Y, X)` 页在前，
  有的写成列在前），绕开它就不用对着改。
- 驱动只有「命令、数据合在一个函数里带 cmd 标志」的写法（正点原子、中景园旧版），
  改成 `OLED_WR_Byte((c), 1)` / `OLED_WR_Byte((d), 0)` 即可，文件里有现成示例。
- 有的工程把 `OLED_WriteCommand` / `OLED_WriteData` 只写在 `.c` 里、没在 `.h` 声明，
  在自己文件里调用会报未声明。把这两行补进 `.h` 即可。
- 屏是 **SH1106**（132 列）时 `ANIM_COL_OFFSET` 要是 `2`，SSD1306 是 `0`。
  这个值导出时已经按驱动源码判断好填进去了（见下面「屏控制器」一节），一般不用管。
- 数组**不是 `static`**，所以**只在一个 `.c` 里 include**，多个文件包含会报重复定义
  （这是故意的：数组可能几 KB，悄悄多占一份 Flash 比链接报错更麻烦）。
- Flash 占用就是文件头部的「数据量」，8 帧 128×64 = 8KB，C8T6 的 64KB 里要算一下。

### 重复帧会自动去掉

GIF 里静止的段落很多：人物眨眼前后十几帧一模一样，各占 1KB 纯属浪费；循环播放的
转圈图标首尾帧也常常相同。导出时会把这些**完全相同的帧只存一份**：

```c
#define ANIM_COUNT       30   /* 播放多少帧 —— 播放循环还是用它 */
#define ANIM_DATA_COUNT  21   /* 数组里实际存了几帧 */
static const uint8_t Anim_Frames[ANIM_DATA_COUNT][ANIM_FRAME_SIZE] = { ... };
static const uint8_t Anim_Map[ANIM_COUNT]  = { 0,1,2,2,2,3, ... };
```

`Anim_Map` 把逻辑帧号指回数据帧号，重复的帧刷同一份数据 —— 画面完全一样，播放
时长也不变，所以**播放代码一个字都不用改**，还是 `for (i = 0; i < ANIM_COUNT; i++)`。

没有重复帧时不生成 `ANIM_DATA_COUNT` 和 `Anim_Map`，输出和以前完全一样，
老工程重新导出不会被搅动。

## 字体：为什么有些字体取出来是糊的

字体下拉框列的是系统里所有字体，但**不是每款字体都有汉字**：

- `Arial`、`Consolas`、`Calibri` 这类西文字体，本来就没有汉字字形；
- Windows 上还有一批「家族名其实是样式名」的，比如
  `Bahnschrift SemiBold Condensed`、`Segoe UI Semilight` —— 选它的时候
  Qt 拿到的字重是 600（SemiBold），而不是普通粗细。

这两种情况 Qt 都会自己找别的字体顶上，**而且把字重一起带过去**：汉字最后是用
「宋体·加粗」画的。16×16 的格子里，加粗宋体一笔两像素，相邻笔画粘成一片，
取出来就是一团糊 —— 字还是那个字，但认不出来。

现在的处理：

1. 选中的字体自己就含汉字 → 原样用（字重是你选的，不动它）；
2. 不含汉字 → 换成一款确定有汉字的字体（宋体 → 黑体 → 微软雅黑 → 等线 → …），
   **字重压回 Normal**，字体框下面给一行黄字说明：
   `⚠「Arial」里没有汉字字形，汉字实际用「宋体」画，字形和这个字体不一样`；
3. 英文字母仍用你选的那款字体画，不受影响。

想让字好看，直接从宋体 / 黑体 / 微软雅黑 / 等线里挑。16×16 推荐**宋体**
（带内嵌点阵位图，笔画最干净），24×24 / 32×32 可以用黑体或雅黑。

### 还有一层：小字号下笔画够不到一个像素

字重回退只管住了「加粗」这一种糊法。还有一种是**抗锯齿**造成的，跟选哪款字体无关。

16×16 的格子里，宋体的一横看着是 1 像素宽。但在矢量字体里它不是 1 像素 ——
是 0.72 像素。画的时候 Qt 会把它摊成一片灰：中间深、两边浅。二值化时阈值切在
哪儿，这一横就在哪儿断、在哪儿变粗；同一个字里上下两横的粗细还不一样。
整块看上去就是糊的。

只有**宋体的 16×16** 躲得过：这款字体自带 12/16 号的内嵌点阵位图，系统直接
给位图，本来就是纯黑纯白，没有灰。

实测「墨迹像素里有多少是半灰」（三个笔画密的字取平均）：

| 字体 | 16px | 24px | 32px |
|------|------|------|------|
| 宋体 | **0%** | 68% | 59% |
| 华文宋体 | 60% | 58% | 51% |
| 微软雅黑 | 61% | 58% | 48% |
| 黑体 | 57% | 57% | 51% |

注意只有宋体那一格是 0 —— 24/32 号连宋体自己也是拿轮廓缩放的，一样糊。

所以现在的做法是先**量一次**：拿当前字体画「嵌温网」三个笔画密的字，算中间灰
的占比；超过 12% 就说明这个字体在这个字号下没有点阵位图，汉字改走**无抗锯齿
渲染** —— 让 Qt 按整像素出图，该一像素就是一像素，不再摊灰。

代价只有一个：这条路下点阵里只有黑和白，**阈值滑块不参与**（宋体 16×16 本来
也是这样，它只有 0 和 255，阈值切在哪儿都一样）。英文字母不受影响，仍走原来的
抗锯齿渲染和各款字体。

换字体、换字号都会重新量，所以从 24 切回 16 会自动回到「宋体自带点阵」那条路。

## 编码格式

```
阴码 / 列行式 / 逆向(低位在前) / C51格式
一个汉字 = 每页 N 字节 × (N/8) 页

    16×16 ->  2 页 × 16 = 32 字节     每行 35 字节（3 + 32）
    24×24 ->  3 页 × 24 = 72 字节     每行 75 字节（3 + 72）
    32×32 ->  4 页 × 32 = 128 字节    每行 131 字节（3 + 128）
```

字号只能是 8 的倍数——编码按页走，一页 8 行，`12×12` 这种除不尽。

导出的头文件开头带了四个宏，**驱动里用它们，换字号就不用改驱动**：

```c
#define OLED_CFONT_W       24   /* 点阵宽 */
#define OLED_CFONT_H       24   /* 点阵高 */
#define OLED_CFONT_BYTES   72   /* 一个汉字多少字节 */
#define OLED_CFONT_STRIDE  75   /* 字库里一行多少字节 */
```

数组名也跟着字号变：`OLED_CF16x16` / `OLED_CF24x24` / `OLED_CF32x32`，
另有 `OLED_CFONT_TABLE` 指向当前这份，`OLED_CFONT_NUM` 是汉字个数。

工程里 `Hardware\OLED.c` 的 `OLED_ShowChinese()` 就是按这个格式取数据。

**换成 24/32 后驱动要跟着改一处**：列宽是 8 像素，一个汉字占 `OLED_CFONT_W / 8`
列（16→2、24→3、32→4）。驱动里如果写死"下一个字 +2 列"，24×24 会叠在一起。
取模工具不碰你的 `OLED.c`，这一步得自己改。

Qt 版实现在 `src\fontgen.cpp`，Python 版在 `src\gen_oled_hz.py`。
**两条独立实现，编码逻辑（分页、位序、字节序）改一边必须同步改另一边。**

实测差异：16×16 两者**逐字节完全一致**（宋体该字号带内嵌点阵位图，两边都直接取位图）；
24×24 / 32×32 因光栅器不同，每字差 1~2 像素，**字形都对，以 GUI 版为准**。

### 取反（反白显示）

文字页和图片页的「取模设置」里各有一个 **取反色（反白显示）** 开关，默认关。

勾上以后点阵的每一位都对调：原来亮的不亮、不亮的地方亮，屏上是**亮底暗字**
（整幅图则是亮底暗图）。字的位置、粗细、大小都不变，只是黑白互换 —— 想做
反白标题条、选中行、或者在亮底上压暗一个 logo 时用它。

三个要知道的点：

- **空格和缺的字会变成一整块亮的**。这是有意的：反白时那一行本来就该连成
  一片亮底，中间豁一个洞反而更怪。
- **字母数字不跟着反白**。ASCII 走驱动自带的 8×16 字库（`CF_SHOW_ASCII`），
  压根不在字库文件里，所以同一行里汉字反白、字母不反白。要整行统一，
  要么只用汉字，要么在驱动里自己对 ASCII 取反。
- **导出的头文件会写明**「本字库已取反」，不会再顶着"阴码"两个字骗人。
  要改回去，把开关关掉重新导出即可。
- **左上角副标题也会跟着变**：没勾是「阴码 · 列行式 · 低位在前 · 字号可选」，
  勾上就变成「反白 · 列行式 · 低位在前 · 字号可选」。取反只对调每一位的值，
  排列方式和位序没动，所以后面那三项照旧。

图片页那个开关是**按素材单独存**的，和阈值、抖动一样；打包导出多份素材时，
文件头会提示"有素材已取反"。

## 显示函数：不用自己写

导出的 `OLED_CFont.h` 里**自带** `OLED_CFont_ShowString()`。不需要你工程里有
`OLED_ShowChinese`，也不用管那个函数的参数顺序、页数算法是怎么写的。

只要把文件里【适配区】的宏指向你驱动的写命令、写数据函数：

```c
#define CF_WRITE_CMD(c)                 OLED_WriteCommand(c)
#define CF_WRITE_DATA(d)                OLED_WriteData(d)
#define CF_SHOW_ASCII(line, col, ch)    OLED_ShowChar((line), (col), (ch))  /* 英文字符 */
```

然后：

```c
#include "OLED_CFont.h"

OLED_Init();
OLED_CFont_ShowString(1, 1, "\xE6\xB8\xA9\xE5\xBA\xA6");            // 温度
OLED_CFont_ShowString(2, 1, "T=25C \xE6\xB9\xBF\xE5\xBA\xA6");      // 中英混排
```

**中文串别手打**——上面那两串 `\xE6\xB8\xA9...` 不是让人手写的。文字页
「① 要显示的文字」下面有个 **「复制为 C 字符串」** 按钮：你分几行，它就生成几句，
行号从 1 递增，中文逐字节转成 `\xNN`。点一下、粘进 `main.c` 就行。

每个字的转义后面紧跟它自己的汉字，一行放不下会自动折行：

```c
OLED_CFont_ShowString(1, 1,
    "\xE5\xB5\x8C"/* 嵌 */ "\xE5\x85\xA5"/* 入 */ "\xE5\xBC\x8F"/* 式 */
    "\xE5\xBC\x80"/* 开 */ "\xE5\x8F\x91"/* 发 */ "\xE7\xBD\x91"/* 网 */
    );
```

相邻的字面量由编译器自动拼接，编出来的字节和写成一整串完全一样；注释里的
汉字不参与编译。这样改字节时不用数位置——哪个字对应哪三个字节，就在旁边。

这么写不只是省事：**源码里没有中文字节**，armcc 按 GBK 解析时没有东西可以吞掉引号，
Keil 保存时把 UTF-8 BOM 弄丢也照样编得过（原因见文末「一处硬要求」那一节）。

`line` 是第几行文字（从 1 开始），`col` 是从第几列开始（单位 8 像素，和
`OLED_ShowString` 的 `Column` 一致）。16×16 的汉字占 2 列，24×24 占 3 列，32×32 占 4 列。

几个要留意的地方：

- **定位命令是函数自己发的**（`0xB0|页`、列地址高低 4 位），不调用 `OLED_SetCursor`。
  各例程这个函数的参数顺序不一致（`OLED_SetCursor(Y, X)` 页在前，有的写成列在前），
  绕开它就不用改。
- 没有英文字符显示函数，就把 `CF_SHOW_ASCII` 改成 `((void)0)`——英文字符被跳过，
  汉字位置仍然连续。
- 屏是 **SH1106**（132 列）时 `CF_COL_OFFSET` 要是 `2`。同样由工具自动判断填好。
- 行号超出屏幕（16×16 只能放 4 行、24×24 放 2 行）时**整行跳过**，不会绕回第 0 页乱画。
  能放几行由 `CF_SCREEN_H` 决定：导出组那个「屏」下拉选 `32 行` 时它会被写成 32，
  128×32 的 0.91" 屏才对得上。
- 字库里没有的字会**占位不画**，后面的字不会挤上来，排版不会错乱。

### 查字是二分，不是遍历

码表在生成时就按 UTF-8 编码升序排好了（UTF-8 的字节序和码点序一致），
所以 `OLED_CFont_Find()` 用二分查：

```c
static const uint8_t *OLED_CFont_Find(const char *utf8)
{
    uint16_t lo = 0, hi = (uint16_t)OLED_CFONT_NUM;
    ...
}
```

70 个字时线性扫和二分没区别；但 300 个字以上，刷一屏 4 行 32 个字就是上万次比较，
刷新率会肉眼可见地掉。二分 500 个字也只要 9 次。

**前提是码表必须有序。** 手改字库（往数组里插一行）就会破坏它，表现是"某几个字
突然显示不出来"，编译链接都不报错。要加字就用工具重新导出，或者用
`add_chars.py` —— 它走同一套排序。
- 原来工程里的 `OLED_ShowChinese` 不用删，两套可以并存。

顺带修掉一个老问题：`add_chars.py` 生成的字库以前末尾**没有 `#endif`**，include guard
形同虚设，两个 `.c` 同时包含会重复定义数组。现在补齐了。

## 一键接入工程

上面那些步骤（驱动头文件补声明、`main.c` 补 `#include`、补示例）不用手工做。
**文字页和图片页各有一个入口**，区别只是接的东西不一样：

| 入口 | 接什么 | 补的示例 |
|---|---|---|
| 文字页：**一键接入工程…** | `OLED_CFont.h`（汉字库） | 两行 `OLED_CFont_ShowString(...)` |
| 图片页：**一键接入工程…** | 上次「全部存进一个 .h」导出的素材包 | 一行 `Xxx_ShowFrame(0)`，先刷第 0 帧 |

素材包那条**只插一行首帧调用，不把播放循环塞进 `while(1)`**：那要动你已有的循环体，
得跳过按键扫描和延时节奏，等于替你决定程序结构。插在 `OLED_Init()` 之后一行，
能立刻看出接线对不对、图是不是这张；真要播动画，把它换成循环即可，预览里会写下怎么换。

流程：

1. 工具自己找工程根（认 `.uvprojx` / `.ewp` / `.cproject` 这些工程文件，不看目录名）
2. 在工程里找**定义了写命令函数的那个 `.c`**（`OLED.c` 也好 `lcd.c` 也好，靠内容判断），
   再找它旁边的 `.h`
3. 找**调用了 `OLED_Init()` 的那个 `.c`**（同样不看文件名）
4. 把各处插入列出来，右边能逐条看插入位置和上下文

每一条都可以单独取消勾选。确认无误点「执行」。

```
OLED.h：补 2 行函数声明      ← 加在 #endif 之前
main.c：补 #include          ← 加在最后一个 #include 之后
main.c：补 2 行示例调用      ← 加在 OLED_Init(); 之后
```

三条底线：

- **只插入，不修改**你已有的任何一行
- 每个文件先备份成 `<文件名>.oledbak`，随时点「撤销上次接入…」还原
- **幂等**：已经补过的东西不会再加第二遍，重复点不会堆出三份声明

几个已经处理掉的坑：

- 头文件里两个文件的行尾不一样（`OLED.h` 是 CRLF、`main.c` 是 LF 还带 BOM），
  工具按各自的原样写回，不会把整个文件的行尾都改掉
- `#include` 的写法**跟着工程走**：`main.c` 里已经用短名包含过同目录的头文件
  （典型是 `#include "OLED.h"`），说明那个目录在 Include Path 上，字库也写短名
  `#include "OLED_CFont.h"`，两行看着是一套规则；没有这个依据就写相对路径
  `../Hardware/OLED_CFont.h`，保证一定编得过
- 驱动里同时有 `OLED_Init` 和 `OLED_I2C_Init` 时，挑**真的在 main 里被调用**的那个
- 找不到 `OLED_Init();` 单独成行时**宁可不插**示例，也不猜位置——插错地方会编译不过
- 示例串写成 **`"\xE5\xBC\xA0"` 这种字节转义**，源码里不留中文字节。屏幕上的字节
  还是 UTF-8 三字节，效果一模一样，但**在 Keil 里改一下那行坐标再保存、BOM 被洗掉，
  也不会报 `#8: missing closing quote`**（原因见下面「中文乱码 / 编译报 #8」一节）

### `OLED_Font.h` 和 `OLED_CFont.h` 不是一份文件

名字只差一个 `C`，接进去的时候最容易看混，但它们完全不搭界：

| 文件 | 是什么 | 谁在用 |
|---|---|---|
| `OLED_Font.h` | 例程自带的 **ASCII 8×16** 字库 | `OLED_ShowChar` / `OLED_ShowString`（字母、数字） |
| `OLED_CFont.h` | 本工具生成的**汉字**点阵库 | `OLED_CFont_ShowString`（汉字） |

两个都要有，各管一半：一行字里既有字母数字也有汉字。

`main.c` 里那两行 `#include` 也**不重复**——`.c` 里的 `#include` 只对那个文件自己有效
（`OLED.c` 里包含过什么，`main.c` 一点都看不到）。`main.c` 要调 `OLED_Init`，
就必须自己看见它的声明：

```c
#include "OLED.h"          /* OLED_Init / OLED_ShowString 的声明 */
#include "OLED_CFont.h"    /* OLED_CFont_ShowString */
```

顺序还有讲究：`OLED_CFont.h` 默认把 ASCII 交给 `OLED_ShowChar` 显示，
所以 `OLED.h` 必须写在它前面。工具补 include 时也是加在**最后一个 include 之后**，
不会插到前面去。

## 屏控制器：SSD1306 还是 SH1106

0.96 寸 OLED 有两种控制器，显存宽度不一样：

| | 显存 | 可见区起点 | 列地址 | 表现 |
|---|---|---|---|---|
| SSD1306 | 128 列 | 第 0 列 | 直接写 0~127 | 正常 |
| SH1106 | 132 列 | 第 2 列 | 都要 +2 | 不 +2 就整幅左移 2 像素、右边少两列 |

这个差别不体现在点阵数据里，只体现在「往哪个列地址写」。所以三份导出文件各自
有一个宏：`CF_COL_OFFSET`、`ANIM_COL_OFFSET`、`OLED_SELFTEST_COL_OFFSET`。

**现在不用自己翻了**。「导出」组上方有个「屏」下拉（左边控制器、右边屏高），默认
「自动判断」，打开工具就去工程里找驱动源码，按内容判断：

- 源码里写了型号（注释里写 `SH1106` / `SSD1306` 最常见）→ 直接定案
- 设列地址的地方多加了 2（`((X + 2) & 0xF0) >> 4`）→ SH1106
- 设列地址时直接用列号、没有偏移 → SSD1306（中景园、正点原子的 SSD1306 例程都这样）
- 出现 `0x83`（132 列末列）→ SH1106
- 出现 `0x21` / `0x22` 寻址命令 → SSD1306

判断结论直接写在下拉框上（例如「自动判断 · SSD1306」），鼠标停上去能看到依据在
哪个文件第几行。判不出来就显示「未识别（先按 SSD1306）」，按最常见的处理。

判错了（表现是整幅左移 2 像素、右边框缺两列）就在下拉里手动选另一项，导出时按你
选的写。

同行的右边那个小下拉是**屏高**：`64 行`（0.96" 128×64）或 `32 行`（0.91" 128×32）。
它只影响字库里的 `CF_SCREEN_H` —— 决定"第几行还放得下"。32 行的屏只有 4 页，
按 64 算会让第 3 行文字往不存在的页地址里写。

几条实现上的讲究：

- **注释里的话不当证据**。驱动注释里写「以前试过 0x02」很常见，所以判代码前先
  把注释剥掉，行号保持不变，证据还能指回原文件。
- **认内容不认文件名**。驱动叫 `OLED.c` / `lcd.c` / `oled_drv.c` 都一样找得到。
- **GBK 工程照样读**。按内容判编码，中文注释不会让判断失效。
- **大小写不敏感**。正点原子写 `0xb0`，中景园写 `0xB0`，两种都认。

## 芯片 Flash 容量

窗口底部第二行会写「Flash 64 KB · 占 3.1%」。这两个数是这么来的：

| 字段 | 来源 |
|---|---|
| 容量 | 工程文件里的 `<IROM><Size>`，也就是链接器实际能用的 ROM 大小 |
| 占比 | 字库字节数 ÷ 容量 |

**芯片型号不摆在状态行上**，鼠标停在它上面才看得到（第一行就是「工程芯片：xxx」）。
原因很简单：这工具不只服务 STM32F103，把型号印在界面上容易被理解成「只认这个型号」。
容量本身照旧跟着工程变 —— 换 512KB 的工程，这行就是 `Flash 512 KB`。

读的是**链接器里的值**，不是从型号猜的。因为有人会把 IROM 改小（比如留一半给
bootloader），这时型号还是 ZE，但可用空间已经不是 512KB 了 —— 按型号算会高估。

同一个工具打开不同工程会自动换。`MyFreeRTOS_C8T6c`（STM32F103C8）显示 64 KB，
`MyFreeRTOS_ZET6k`（STM32F103ZE）显示 512 KB，不用手改。

读不到时按类型往下退，每一步都在 tooltip 里写清用了哪条：

1. Keil 工程 `.uvprojx` 的 `<IROM><Size>`
2. CubeIDE / Makefile 工程的链接脚本 `FLASH (rx) : ORIGIN = ..., LENGTH = 512K`
3. IAR 工程 `.icf` 里的 `__ICFEDIT_region_ROM_size__`
4. 型号解码：`STM32F103ZE` 末位 `E` = 512KB（ST 命名规则）
5. 都没有 —— 显示「按 64 KB 估」，不假装读到了

末尾那个小下拉可以手动指定容量（32 KB ~ 1 MB），覆盖自动值。什么时候用得上：

- 工程文件读不出来（老工程、非 Keil/IAR/CubeIDE 的奇怪构建）
- 你把 Flash 分了一部分给别的东西，想按剩下的空间算

图片 / 动画页的占用提示也跟着这个容量走：同样是 20 KB，在 64 KB 的芯片上占 31%
（橙色警告），在 512 KB 上只占 3.9%（绿色）。

## 一处硬要求：UTF-8，而且**带 BOM**

`OLED_CFont.h` 必须写成 **UTF-8**，且 Keil 的
`Edit → Configuration → Encoding` 要选 **UTF-8**。工具已经按 UTF-8 写出，
但如果你用别的编辑器打开再保存，可能被转成 GBK，字库就会查不到。

更麻烦的是另一半：**你自己的 `main.c` 也必须带 UTF-8 BOM。**

Keil 的编译器 armcc（AC5）不看文件内容判编码，一律按系统代码页（中文系统是 GBK）
当双字节解析。汉字在 UTF-8 里是三字节，比如「张」= `E5 BC A0`，最后那个 `A0`
落在 GBK 的引导字节区间，它会把后面那个**引号**当成自己的第二字节吞掉，于是：

```c
OLED_CFont_ShowString( 3, 4, "张" );    /* 源码里看着没问题 */
```
```
User\main.c(12): error:  #8: missing closing quote
OLED_CFont_ShowString( 3, 4, "寮?" );
User\main.c(14): error:  #18: expected a ")"
```

报错行号会飘到下一行语句上，而且文件本身完全合法 —— 纯粹是编译器读错了字节。
注意 Keil 编辑器里 Encoding 选 UTF-8 时，它保存出来的文件是**不带 BOM** 的，
所以照上面那句设置完，中文串反而编不过，很容易以为是工具导出的字库坏了。

两个解法，任选一个：

1. **给源文件补 UTF-8 BOM**（推荐）。`scripts\add_bom.py main.c` 就行；
   用本工具「一键接入工程」写回时也会自动补（写中文时才补，纯 ASCII 的文件不动）。
2. 工程 `Options → C/C++ → Misc Controls` 加 `--locale=english`。
   这会让 armcc 不再套本地代码页，UTF-8 字节原样通过。改一次整工程有效。

四条路都用 AC5.06u5 实测过（就是 Keil 里那个 armcc，命令行直编，
工程里那一整套 `-I` 原样带上）：

| 源文件 | 编译 | 目标文件里的字符串 |
|---|---|---|
| UTF-8 **无** BOM + `"张"` | ❌ `#8` / `#18` | — |
| UTF-8 **有** BOM + `"张"` | ✅ | `E5 BC A0` ✓ |
| UTF-8 无 BOM + `"\xE5\xBC\xA0"` | ✅ | `E5 BC A0` ✓ |
| UTF-8 无 BOM + `"张"` + `--locale=english` | ✅ | `E5 BC A0` ✓ |

**但 `--locale=english` 有个反噬：** 它让 armcc 对所有源文件都不再转码，
按字节原样送进去。所以哪天谁用 ANSI / GBK 存了一份带中文串的 `.c`，
会**编译通过、屏幕一个字不显示**（实测这种文件编出来的目标里是 `D5 C5`，
不是 `E5 BC A0`，和字库的键对不上）。用这个开关的前提是：工程里所有
含中文串的源文件都统一是 UTF-8。

**补 BOM 得反复补。** Keil 的编辑器保存时会把它去掉 —— 实测：文件本来带 BOM，
在 Keil 里把那行坐标从 `(1, 1)` 改成 `(3, 4)`、按 Ctrl+S，BOM 就没了，
编译立刻报 #8。所以本工具写进去的示例串也不用中文，直接写字节转义：

```c
OLED_CFont_ShowString( 1, 1, "\xE5\xBC\xA0" );   /* 屏幕上显示「张」 */
```

源码里一个中文字节都没有，BOM 在不在都能编过。**你自己写的**中文串没有这层保护，
还是得靠 BOM 或 `--locale=english`；工具右侧的「源码编码」那行会盯着，
一旦检测到「UTF-8 但缺 BOM」就会标黄提醒。

### 一句话总结怎么避

- **别在 Keil 编辑器里改含中文串的源文件** —— 它保存时按自己的 Encoding 重写整个
  文件，BOM 说没就没。非要用它改，改完跑一次 `scripts\add_bom.py`。
- 能把中文串换成 `"\xE5\xBC\xA0"` 就换掉：源码纯 ASCII，任何编辑器、
  任何编码设置、AC5 还是 AC6 都不会再有这个问题，也不需要再维护 BOM。
- 懒得换就上 `--locale=english`（一次改工程、永久生效），前提是工程里的中文串
  统一是 UTF-8 文件。

另外，AC6（armclang）默认按 UTF-8 读源码，不受这条影响。
